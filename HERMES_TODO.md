## 2. Architectural Flaws

### A. No Separation of Concerns

`project-lms.py` is a 1068-line single file containing:
- Presentation (customtkinter widgets, layouts, animations)
- Business logic (borrow/return/delete/search workflows)
- Data access (direct `self.db._execute_query()` calls)
- Event handlers (button callbacks nested inside `__init__` methods)

There is no MVC, MVP, or MVPVM pattern. The GUI layer talks directly to the database layer.

### B. Missing CRUD Methods in DatabaseManager

`lms-cli.py` calls methods that **do not exist** in `database.py`:

| CLI calls | Exists in DB? |
|---|---|
| `db.add_tool(...)` | ❌ NO — GUI uses `db.insert_tool(...)` |
| `db.update_tool(tool_id, **updates)` | ❌ NO — only `db.update_tool_quantity(tool_id, qty)` exists |
| `db.clear_tables()` | ❌ NO — only `db.clear_users()` exists |

The CLI will **crash at runtime** when a user tries to add, update, or clear data.

### C. Signature Mismatch — `return_tool`

- `DatabaseManager.return_tool(tool_id, user_id, return_date)` — requires 3 args
- CLI `handle_return_tool` calls `db.return_tool(tool_id)` — passes only 1 arg → **Runtime crash**
- GUI `return_tool()` does its own ownership check via SQL JOIN (bypassing the DB method entirely)

### D. Two Database Files, One Schema

- `db/inventory.db` — used by both GUI and CLI
- `db/users.db` — created but **never referenced in code** (dead file)
- The `users` table lives in `inventory.db`, not `users.db`
- The README claims `users.db` exists as a separate account database — this is misleading

### E. No Dependency Injection

`DatabaseManager` is instantiated with a raw path string everywhere. No interface abstraction, no repository pattern, no service layer. This makes unit testing difficult (the existing tests work around it by creating temp DB files, but they're standalone scripts, not a test suite).

### F. Magic Numbers & Hardcoded Values

- Window sizes (`1280x800`, `420x600`, etc.)
- Font sizes (`int(win_height * 0.035)`)
- Color hex codes (`#23272f`, `#4f8cff`, etc.)
- Animation step counts (`step / 12`)
- Layout padding values

None of these are configurable or themed.

### G. Dead Schema Objects

- `students` table — created in `create_tables()` but **never read or written** anywhere in the codebase
- `users.db` file — exists on disk but is never opened by any code path
- `check_and_add_default_data()` — stub that does nothing

### H. No Connection Management

- Single `self.conn` per `DatabaseManager` instance, never pooled
- `ensure_connection_open()` is a band-aid for silent connection deaths
- No WAL mode, no timeout, no concurrent access strategy
- No connection closing on errors

## 3. Security Issues

### Critical

1. **IDOR in CLI `return_tool`** — The CLI path calls `db.return_tool(tool_id)` with no user context, allowing any user to return any borrowed tool. The GUI fixed this with a JOIN on transactions, but the CLI was never updated.

2. **Arbitrary SQL Execution** — `handle_execute_sql()` in the CLI allows any user to run `DROP TABLE`, `DELETE FROM users`, etc. The only guard is checking if the command starts with `select`. This is a **critical privilege escalation vector**.

3. **No Authorization / Role-Based Access Control** — The README mentions Admin vs Regular User roles, but there is no implementation. Every user can delete tools, execute SQL, and clear all data. The `clear_tables()` method (which doesn't exist yet) is labeled "Admin Only" in the menu but has no access control.

### High

4. **Fragile Password Hash Encoding** — `get_user()` does string→bytes conversion with UTF-8/latin-1 fallback. If a hash was stored in a different encoding, login silently fails. The `insert_user` stores bcrypt hashes as BLOB but reads them back as strings.

5. **No Brute-Force Protection** — Login allows unlimited attempts with no rate limiting or account lockout.

6. **No Password Complexity** — Signup only requires `len(password) >= 6`. No uppercase, digit, or special character requirements.

7. **No Session Management** — `user_id` is stored as a plain instance variable with no session token, expiry, or invalidation mechanism.

### Medium

8. **No Input Validation on GUI Fields** — Tool name, category, condition, location all accept arbitrary strings. While SQL injection is mitigated by parameterized queries, there's no business-logic validation (e.g., empty strings, SQL-injection-like content in text fields).

9. **Background Image Path Traversal Risk** — `os.path.join("assets", "background_image.jpg")` is relative to CWD. If the working directory changes, the app could load unexpected files.

10. **No Logging to File** — All logging goes to stdout only. No file handler, no rotation, no audit trail for security-relevant events (logins, deletions, SQL execution).

## 6. Team Refactoring Strategy

### Phase 2 — Safe Refactoring (No file modifications until Phase 3)

**Squad Composition:**

| Role | Responsibility |
|---|---|
| **Architect** | Design the module boundaries, seam locations, and interface contracts |
| **Senior Developer** | Implement the refactored modules, migrate logic incrementally |
| **QA** | Write integration tests, verify no regressions, validate security fixes |
| **Security Engineer** | Audit auth flows, fix IDOR in CLI, add RBAC, harden inputs |

### Step 1: Extract DatabaseManager Interface (Architect + Senior Dev)
- Define a `ToolRepository` protocol (interface) with typed methods
- Make `DatabaseManager` implement that protocol
- Add missing methods: `add_tool`, `update_tool`, `clear_tables`
- Fix `return_tool` signature in CLI to pass `user_id` and `return_date`

### Step 2: Separate GUI from Business Logic (Architect + Senior Dev)
- Extract all `ToolManagementApp` business methods into a `ToolService` class
- GUI becomes a thin view layer that calls `ToolService` methods
- `LoginApp` becomes a separate view with its own controller

### Step 3: Fix CLI Gaps (Senior Dev + Security Engineer)
- Fix `handle_return_tool` to pass user context (3 args)
- Remove `handle_execute_sql` or restrict to admin role
- Add `add_tool`, `update_tool`, `clear_tables` implementations to `database.py`
- Add role check before admin-only operations

### Step 4: Security Hardening (Security Engineer)
- Add RBAC (admin vs user roles in the `users` table)
- Implement login rate limiting
- Add password complexity requirements
- Add session tokens with expiry
- Replace arbitrary SQL execution with a whitelist of safe queries
- Add audit logging to file

### Step 5: Test Infrastructure (QA)
- Convert standalone test scripts to pytest suite
- Add test fixtures for temp database setup/teardown
- Add coverage reporting
- Add CI pipeline config
- Add integration tests for all CRUD operations via both GUI and CLI paths

### Step 6: Configuration & Polish (Senior Dev)
- Extract magic numbers into a config file or constants module
- Add `.gitignore` for `__pycache__`, `.db`, `.pyc`
- Add `pyproject.toml` with proper packaging metadata
- Set up virtualenv in `.venv/`
